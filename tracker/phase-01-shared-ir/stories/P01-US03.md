# P01-US03 — Generate canonical presentation blocks

Status: Done  
Story points: 5  
Phase: Phase 1 — Shared IR  
Priority: High  
Dependencies: P01-US02  
Feature flag: `parser.canonical_serialization.enabled`

## User story

As an API consumer, I want Markdown and text generated from one authoritative IR
presentation contract, so that different clients cannot reinterpret content.

## Business value

Eliminates caption-only, caption-plus-OCR, and OCR-only variants of the same item
and stabilizes RAG/indexing inputs.

## Problem statement

Backend Markdown, frontend Markdown, and frontend plain text currently apply
different image rules.

## In scope

- Canonical per-element and per-page presentation blocks.
- Rules for captions, subordinate OCR, tables, images, headers, and footers.
- Duplicate suppression based on element/relationship IDs.

## Out of scope

- Frontend migration.
- New extraction or repair.
- Removal of legacy fields.

## Technical approach

Generate canonical Markdown/text from ordered IR, retain structured JSON as the
source of evidence, and expose compatibility blocks behind a flag.

## Acceptance criteria

1. Each semantic element appears at most once in canonical output.
2. Captions and subordinate OCR follow explicit type/relationship rules.
3. Tables retain span-capable HTML where required.
4. Canonical output is deterministic across repeated runs.
5. Flag-off output remains unchanged; flag-on differences are fixture-reviewed.

## Dedicated tests

- Unit tests: [tests/stories/phase_01/test_p01_us03_canonical_presentation.py](../../../tests/stories/phase_01/test_p01_us03_canonical_presentation.py)
- Integration tests: full catastrophe page and direct-image item stream.
- Negative tests: duplicated relationships, empty image, caption/OCR conflict.
- Contract tests: Markdown content type, JSON additive fields, legacy fallback.
- Fixture-based tests: Phase 00 outputs.

## Regression impact

Run Phase 00–01, all serializers, API, table HTML, and image presentation tests.

## Metrics

- Before: three divergent presentation rules.
- Target: one canonical block per element; 0 duplicate semantic elements.
- After: `../metrics.md`.

## API and schema compatibility

Potential Markdown behavior change only when flagged. JSON changes are additive.

## Risks

- Intended presentation changes may affect downstream snapshots.
- Canonical blocks could hide useful subordinate evidence if rules are too strict.

## Rollback

Disable canonical serialization and use the legacy backend/client paths.

## Benchmark evidence — LlamaParse-15

- Related gaps: `GAP-SERIALIZATION-001`, `GAP-LAYOUT-001`, and
  `GAP-TABLE-003`.
- Cases/pages/regions: clean-energy p1 chart and false right-edge OCR; health-report
  p1 Figure 3.10 plus overlapping false table; esg-metrics p1 donut with
  concatenated native/caption/OCR labels; uber-earnings p1 false photograph
  caption, p2 duplicated chart endpoints, and p3 duplicated footer logo.
- Current behavior: alternate/native/OCR representations are intentionally
  propagated into standalone Markdown, so one visual element may appear twice
  or a false caption can become primary content. Header/footer/page-body
  inclusion is not a first-class contract.
- Generalized behavior: ordered IR produces one canonical block per semantic
  element; subordinate OCR and alternate structures remain inspectable evidence
  but enter primary Markdown only through explicit relationship and confidence
  rules.
- Acceptance tests: positive—finance-10k tables and settlement-agreement prose
  remain byte-stable; target—the cited chart/image/table/logo overlaps serialize
  once; non-target—distinct repeated labels at different bboxes and reviewed
  source captions remain present; negative—duplicate relationships, empty image
  blocks, caption/OCR conflicts, footer omission, and unsupported primary OCR
  fail deterministically.
- Metrics/performance: 0 duplicate semantic elements, 100% deterministic
  canonical blocks, and reviewed header/footer inclusion on 15/15 cases. Measure
  output-size and p50/p95/RSS deltas against P00-US10 and keep total Phase 01 p95
  overhead at or below 5%.
