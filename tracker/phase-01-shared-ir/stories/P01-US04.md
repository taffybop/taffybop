# P01-US04 — Enforce backend/frontend serialization parity

Status: Done  
Story points: 5  
Phase: Phase 1 — Shared IR  
Priority: High  
Dependencies: P01-US03  
Feature flag: `parser.canonical_serialization.enabled`

## User story

As a user of either API or UI downloads, I want identical canonical content, so
that the selected surface does not change document meaning.

## Business value

Prevents hard-to-debug indexing and review discrepancies across backend and UI.

## Problem statement

The attached Markdown came from frontend `item.md`, while the backend would
prefer a content-region caption and plain text prefers image OCR.

## In scope

- Frontend consumption of canonical blocks.
- Backend/frontend parity contracts for JSON, Markdown, and text.
- Compatibility behavior for older responses without canonical blocks.

## Out of scope

- New extraction features.
- Removal of public legacy fields.

## Technical approach

Make clients render, not parse, the normalized response. Add cross-language
fixtures and byte/semantic parity tests.

## Acceptance criteria

1. Backend and frontend document Markdown are byte-equivalent for shared fixtures.
2. Text views contain the same ordered semantic elements, and canonical UI
   rendering retains their user-visible structural types. In particular,
   included heading blocks render as semantic heading elements using the
   source heading level rather than being flattened to paragraphs, and every
   top-level canonical block exposes its authoritative item type for rendered
   grouping/audit capture.
3. Older additive schemas retain documented fallback behavior.
4. JSON evidence fields are not dropped or reinterpreted by frontend normalization.
5. Supported Node and Python suites pass.

## Regression impact

Run Phase 00–01, backend API/serializer suites, frontend build/unit/bundle tests.

## Metrics

- Before: known content divergence.
- Target: 100% byte parity for Markdown; 100% semantic parity for text.
- After: `../metrics.md`.

## API and schema compatibility

No endpoint change. Frontend fallback preserves older responses.

## Risks

- Frontend runtime/version differences.
- Whitespace-only changes causing downstream snapshot churn.

## Rollback

Disable canonical serialization and restore legacy frontend selection rules.

## Benchmark evidence — LlamaParse-15

- Related gaps: `GAP-SERIALIZATION-001` and `GAP-TABLE-003`.
- Cases/pages/regions: all 15 JSON/Markdown pairs; insurance-acord p1 verified
  footer at `y=747–768`; health-report p1 page marker/footer; esg-metrics p1
  navigation/footer; ny-timetable pp1–3 header/body/footer views.
- Current behavior: our standalone Markdown is the exact ordered non-empty JSON
  item projection in 15/15 cases, but backend/frontend parity is not yet one
  versioned contract. In the expert bundle, 13/15 standalone files differ from
  JSON page-body Markdown; insurance-acord uniquely omits its verified JSON
  footer, showing why implicit inclusion rules are unsafe.
- Generalized behavior: server and client render the same canonical blocks and
  declare full-document, page-body, header/footer, item, and fallback semantics
  without re-parsing evidence.
- Acceptance tests: positive—round-trip all 15 canonical JSON/Markdown/text
  fixtures through Python and supported Node; target—preserve the cited
  headers/footers exactly once; non-target—older additive responses use the
  documented fallback; negative—missing canonical blocks, unknown additive item
  types, evidence-field loss, footer omission, and whitespace/order divergence
  fail parity checks.
- Metrics/performance: 100% byte-equivalent Markdown, 100% ordered semantic-text
  parity, 0 dropped evidence fields, and 0 v1 contract failures. Record backend
  and frontend p50/p95 plus bundle impact; combined Phase 01 p95 overhead remains
  at or below 5% over P00-US10.
- 2026-08-13 functional-fidelity regression: canonical rendered captures for
  `purchase-agreement` p1 must expose `ASSET PURCHASE AGREEMENT` and
  `Background` with `.parsed-heading` semantic heading tags while preserving
  the canonical block text, exact source heading level, and validated text-run
  overlay. Every captured top-level block must also retain `data-item-type` in
  canonical order. The same renderer is used by the interactive UI and the
  repository capture harness.
