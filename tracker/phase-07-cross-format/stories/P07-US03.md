## User story

As a platform operator, I want OOXML packages inspected within strict security
and resource limits, so that DOCX, PPTX, and XLSX support cannot introduce
archive, XML, relationship, or external-fetch vulnerabilities.

## Business value

Provides one reviewed intake boundary for all Office adapters, avoids duplicated
security logic, and fails hostile files before format-specific parsing.

## Problem statement

OOXML files are ZIP packages containing XML, relationships, and potentially
active or external content. Path traversal, archive expansion, XML abuse,
encrypted/macro-enabled files, malformed relationships, and oversized part
graphs require controls before semantic extraction.

## In scope

- MIME/extension/signature, ZIP central-directory, part-name, content-type, and
  relationship validation.
- Safe non-executing XML parsing and deterministic package/part manifest.
- Compressed/uncompressed bytes, entry count, XML nodes/depth, relationship
  count, part size, and processing-time limits.
- External, macro, encrypted, missing, duplicate, and unsupported part policy.
- Read-only bounded part access for format adapters.

## Out of scope

- DOCX, PPTX, XLSX semantic extraction.
- Executing macros, fields, formulas, external links, or embedded programs.
- Password decryption, legacy binary Office formats, rendering, or network
  retrieval.

## Technical approach

Validate the package before exposing any part, canonicalize part paths within
the archive root, parse XML with unsafe features disabled, inventory
relationships without resolving external targets, and enforce cumulative
budgets throughout intake.

## Acceptance criteria

1. Valid DOCX/PPTX/XLSX controls produce deterministic part, content-type,
   relationship, size, hash, and security-policy manifests.
2. Path traversal, absolute paths, duplicate/conflicting parts, unsafe XML,
   malformed relationships, and archive-bomb controls are rejected before
   adapter parsing.
3. External relationships, macros, and encrypted packages are never executed or
   fetched and follow explicit allow/deny/unsupported policy.
4. Every byte/entry/XML/relationship/time limit is enforced at its boundary
   with a reason-coded concern and no partial semantic output.
5. Intake performs zero network access and writes no package part outside its
   bounded temporary/read-only abstraction.
6. Flag-off requests retain the prior unsupported-format behavior.

## 2026-08-13 upload-boundary follow-up

The public upload ceiling is now exactly 20 MiB (`20 * 1024 * 1024` =
`20,971,520` bytes) in the backend configuration/default environment path and
the frontend preflight contract. Exactly 20 MiB is accepted and one byte more
is rejected with the existing reason-coded 413 response. This change does not
alter independent OOXML package, compressed-part, expanded-part, font, model,
or other internal safety budgets. Dedicated boundary coverage is in
`tests/test_api.py` and `frontend/tests/document-api.test.mts`; the retained
LlamaParse-15 artifact manifest verifies that the largest benchmark input is
7,584,019 bytes.

## API and schema compatibility

This story does not advertise Office parsing. Intake diagnostics are internal;
flag-off and unsupported-format public behavior remain unchanged.

## Risks

- ZIP/XML parser behavior can vary across library versions.
- Legal but unusual relationship graphs may trigger false rejection.
- Aggregate expansion and deeply connected parts can exhaust resources.
- New dependencies require security and license review.

## Rollback

Disable OOXML intake and leave DOCX/PPTX/XLSX unsupported. Do not bypass intake
to enable a format adapter.
