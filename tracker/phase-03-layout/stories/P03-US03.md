# P03-US03 — Associate source notes and footnotes

Status: Done  
Story points: 5  
Phase: Phase 3 — Layout  
Priority: High  
Dependencies: P03-US01, P03-US02  
Feature flag: `PARSER_LAYOUT_SOURCE_NOTES_ENABLED` (default off; runtime
binding for `parser.layout.source_notes.enabled`)

## User story

As an auditor, I want source notes and footnotes linked to their elements, so that
citations survive even when they lie outside detected object crops.

## Business value

Restores `Data: Aon Catastrophe Insight` and generalizes to table/chart notes
without increasing every crop.

## Problem statement

The chart bbox ends above the source note, 3pt crop padding misses it, and damaged
native text leaves no alternative path.

## In scope

- Declared graph links and geometry/style proximity candidates.
- `source_note_of`/`footnote_of`, own bbox, text evidence, order.
- Ambiguity and orphan-note concerns.

## Out of scope

- Arbitrary semantic citation inference.
- Increasing global crop padding.
- Text repair implementation.

## Technical approach

Identify small external note candidates below/near structured elements, combine
graph and geometry evidence, and keep notes as distinct elements.

## Acceptance criteria

1. The Aon source note appears once and links to the chart.
2. Its bbox remains outside the chart bbox.
3. Unrelated nearby footer/prose is not linked.
4. Multiple plausible owners produce an ambiguity concern.
5. Notes remain available even when owner OCR crop excludes them.

- Unit tests: proximity/style/ownership scoring.
- Integration tests: [tests/stories/phase_03/test_p03_us03_source_notes.py](../../../tests/stories/phase_03/test_p03_us03_source_notes.py)
- Negative tests: nearby footer, two owners, orphan note, distant note.
- Contract tests: relationship and canonical ordering.
- Fixture-based tests: chart/table footnotes across PDF and image layouts.

## Regression impact

Run Phase 00–03, footer/header, table/image, text integrity, and serializers.

## Metrics

- Before: source-note recall 0/1.
- Target: 1/1; false association 0 on negative fixtures.
- After: `../metrics.md`.

## API and schema compatibility

Adds note elements/relationships behind flag; no endpoint change.

## Risks

- False links in dense multi-object pages.
- Note text may require Phase 02 repair.

## Rollback

Disable source-note association; keep unlinked text evidence if independently emitted.

## 2026-08-14 captioned unresolved-owner UI supersession

This append-only note supersedes only the preceding statement that the
Clinical unresolved owner renders as a non-authoritative paragraph. It does
not change the settled caption/note ownership, public order, backend item type,
historical completion metrics, or frozen functional-fidelity mapping.

A later release composition exposed two generic frontend assumptions. First,
the canonical `table_candidate` block contains the consumed caption followed
by the owner text/Markdown, while the public caption and owner remain distinct
items. Second, canonical relationship IDs (`rel-*`) and public compatibility
relationship IDs (`layout-rel-*`) are intentionally different identity
domains. Exact bare-owner matching and cross-domain ID equality therefore
rejected valid captioned candidates and fell back to paragraph rendering.

The production frontend now resolves the composition only after independently
proving one internal consumed-caption assertion, one complete reciprocal
public `caption_of` graph, strict unresolved-candidate eligibility, exact
bounded caption-plus-owner equality in both text and Markdown, and exactly one
matching pair. Duplicate pairs, split/cross-pair graphs, weak candidates,
tampering, or malformed evidence fail closed to the canonical fallback. The
generic implementation is in
[`layout-relationships.ts`](../../../frontend/lib/layout-relationships.ts) and
[`clearleaf-workspace.tsx`](../../../frontend/app/clearleaf-workspace.tsx); no
backend production file changed in this correction.
