# P00-US01 — Define benchmark manifest and metric contracts

Status: Done  
Story points: 3  
Phase: Phase 0 — Baseline  
Priority: High  
Dependencies: None  
Feature flag: None — test/planning infrastructure only

## User story

As a parser maintainer, I want versioned benchmark and metric contracts, so that
every later story reports comparable, reproducible before-and-after evidence.

## Business value

Prevents subjective quality claims, silent metric drift, and implementation work
that cannot prove improvement or regression.

## Problem statement

The assessment contains strong one-off evidence, but the repository has no common
schema for fixture identity, ground-truth type, run environment, quality metrics,
performance metrics, or unsupported artifacts.

## In scope

- Versioned schemas for benchmark manifests, annotations, run records, and metrics.
- Explicit truth classes: visible text, native data, embedded data, measured,
  inferred, and unknowable.
- Validation errors and a minimal synthetic contract fixture.

## Out of scope

- Registering the catastrophe artifact.
- Changing parser behavior or public API.
- Choosing quality thresholds for later phases.

## Technical approach

Define small machine-readable contracts under `tests/benchmarks/` and validation
helpers used only by tests/reporting. Keep source-output snapshots separate from
ground truth.

## Acceptance criteria

1. Every contract has a version, required fields, units, and documented semantics.
2. Valid synthetic manifests and metric records round-trip deterministically.
3. Missing hashes, unknown truth classes, invalid tolerances, and negative timings fail with actionable errors.
4. Contracts record parser/model versions, commands, hardware, fixture hashes, and output hashes.
5. No production import path, endpoint, or serialized output changes.

## Dedicated tests

- Unit tests: [tests/stories/phase_00/test_p00_us01_metric_contracts.py](../../../tests/stories/phase_00/test_p00_us01_metric_contracts.py)
- Integration tests: validate a complete synthetic run record.
- Negative tests: malformed version, hash, tolerance, units, and metric values.
- Contract tests: schema backward-read behavior for the initial version.
- Fixture-based tests: minimal inline/synthetic manifest; no external document required.

## Regression impact

Run `tests/stories/phase_00/`, `tests/contract/`, and the existing backend suite.

## Metrics

- Before: no shared benchmark/metric contract.
- Target: 100% valid controls accepted; 100% invalid controls rejected.
- After: recorded in `../metrics.md` and `../evidence/P00-US01-*`.

## API and schema compatibility

No public API impact. New schemas are test/reporting artifacts only.

## Risks

- Overfitting the contract to one parser or document type.
- Confusing measured chart values with literal source truth.

## Rollback

Remove the unreferenced test/reporting contracts and their tests; production is
unchanged.
