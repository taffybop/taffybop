## Release-first completion comment

Implemented a pure offline, bounded functional smoke gate that pins known-good
and candidate parser, configuration, artifact-manifest, API-schema, and hosted-
policy identities. It compares only required public-flow success/status/schema
and expected core-content digests, binds the candidate to passing P08-US08 and
P08-US09 outcomes, requires an available exact known-good rollback target, and
emits a deterministic machine-readable decision. Every flow and rollback
target is bound to a canonical digest of the complete release pin, input
iterables are consumed to a hard cap, unexpected coverage is rejected, and
successful parses must carry 2xx status. Any incomplete or failing
input blocks the candidate and retains known-good; the gate performs no
promotion or deployment. Focused validation: `26 passed, 0 failed, 0 skipped,
0 deselected, 1 warning`; cumulative Phase 08 validation through P08-US10:
`166 passed, 0 failed, 0 skipped, 0 deselected, 1 warning`. The warning was
FastAPI's `StarletteDeprecationWarning` at
`.venv/lib/python3.13/site-packages/fastapi/testclient.py:1` for the deprecated
`httpx` TestClient integration. The representative public API success,
ordinary invalid-PDF failure, and rollback-block smoke was `3 passed, 0 failed,
0 skipped, 0 deselected, 1 warning`; the failing candidate left the pinned
known-good identity selected. No live external call or deployment occurred.
Deferred traffic canaries, all-corpus/Llama campaigns, latency/RSS/cost
percentiles, exhaustive quality/statistical gates, and environment-specific
promotion proof were not run or claimed.

## User story

As a release owner, I want a version-pinned candidate compared with the
known-good release, so that incompatible, ungrounded, over-budget, or
policy-failing changes cannot be promoted.

## Business value

A blocking canary gate converts quality, resource, compatibility, artifact, and
privacy evidence into one auditable release decision.

## Problem statement

Earlier stories provide metrics and policies, but no single comparison
reconciles them against a pinned known-good release and fails promotion with
actionable reasons.

## In scope

- Candidate/known-good identity and configuration pinning.
- Frozen-corpus comparison by document/content category.
- Quality, provenance, concern, compatibility, resource, escalation, review,
  and cost checks against approved gates; latency against only paired
  LlamaParse evidence.
- Artifact/license and hosted-policy gate inclusion.
- Machine-readable blocking decision and human-readable summary.

## Out of scope

- Automatic production promotion.
- Live customer traffic or uncontrolled shadow processing.
- Waiving a failed gate without an approved decision record.

## Technical approach

Run candidate and known-good profiles on the same reference environment and
fixtures, normalize only approved nondeterminism, and evaluate explicit
thresholds. Aggregate upstream gate evidence without hiding the originating
failure.

## Benchmark evidence — LlamaParse-15

- Blocking cases: NY grid collapse/silent diagnostics; Postal final-row loss and
  false OCR; purchase redline/order; settlement hyphen; Uber caption/identity/
  chart/diagram/bbox/origin/duplication/page-label failures.
- Coverage blocker: no direct-image, scanned, DOCX, PPTX, or XLSX semantic
  twins currently prove the Phase 07 release profile.
- Performance evidence: historical current-parser totals remain in immutable
  local-baseline artifacts but have no stage/resource attribution, are not
  LlamaParse measurements, and cannot serve as live thresholds.
- Generalized behavior: the canary represents every named gap, preserves
  case/page/region traceability in evidence, fails closed on missing required
  category/twin coverage, compares quality/compatibility/resource/review/cost
  results against their approved gates, and compares end-to-end latency only
  against paired LlamaParse p50/p95.
- Controls: verified source elements are positives; disabled/unchanged routes
  are non-targets; each named gap, missing coverage, and budget/policy failure
  is a negative that must block.
- Gaps: `GAP-VISUAL-001`, `GAP-CHART-001`, `GAP-CHART-002`,
  `GAP-DIAGRAM-001`, `GAP-BBOX-001`, `GAP-PROVENANCE-001`,
  `GAP-DIAGNOSTICS-001`, `GAP-SERIALIZATION-001`, `GAP-PAGE-001`,
  `GAP-COVERAGE-001`, and `GAP-PERFORMANCE-001`.

## Acceptance criteria

1. Candidate and known-good parser, artifact, configuration, calibration, and
   policy versions are pinned in every comparison.
2. The gate compares every approved category for missing, duplicate,
   fabricated, ungrounded, and incompatible output.
3. It compares candidate end-to-end p50/p95 latency only with paired
   LlamaParse p50/p95 per case, while CPU, peak RSS/GPU, escalation/review rate,
   and attributable cost use their independent approved budgets.
4. Any critical quality, API/schema, artifact/license, privacy, or unexplained
   budget failure blocks promotion with its originating evidence.
5. Approved nondeterministic fields are enumerated; no semantic content is
   normalized away.
6. Repeating the gate on identical versions produces the same decision and
   stable quality counts.
7. The decision explicitly represents all eleven named LlamaParse-15 gaps and
   blocks when an applicable gap assertion or required M5 semantic-twin class
   is absent, failed, stale, or unexplained.
8. Latency comparison follows the canonical paired protocol below. Stage and
   component p50/p95 remain diagnostic only; CPU, peak RSS/GPU, and
   instrumentation resource overhead remain independent gates. A single
   total-duration observation cannot satisfy or waive latency.

The sole operative latency benchmark is
[`latency-reference-v1.md`](../../benchmarks/llamaparse-15/latency-reference-v1.md),
including its full 15-case production release screen. It pins LlamaCloud Parse
v2, Agentic mode at 10 credits/page, cost optimizer off, cache disabled, and
provider-UI Total Latency. The initial 2026-08-08 one-sample/case values are
planning/reference ceilings only. Before Definition of Done, collect at least
five interleaved candidate/Llama samples per applicable case. Candidate p50 and
nearest-rank p95 must each be no greater than the paired Llama values for that
same case; corpus averages cannot mask a slow case, no failure may be dropped,
and required quality/reliability must remain unchanged. A path without
semantically comparable Llama input/output is `Unmeasured/Blocked`; historical
candidate/known-good totals and local stage/component timing cannot substitute.
Known-good release comparison remains operative for every non-latency gate.

No parse response change. Canary reports and gate decisions are operational

## Risks

- A frozen corpus can miss production drift.
- Broad normalization can hide real semantic changes.
- Noisy resource measurements can cause unstable decisions.

## Rollback

Block the candidate and retain the pinned known-good release. A failed gate
requires corrected evidence or an explicit time-bounded decision record.
