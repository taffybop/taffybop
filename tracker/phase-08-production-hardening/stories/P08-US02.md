# P08-US02 — Add privacy-safe telemetry primitives and exporter isolation

Status: Done — release-first core functionality validated  
Completed: 2026-08-12  
Story points: 5  
Phase: Phase 8 — Production Hardening  
Priority: High  
Dependencies: P08-US01  
Feature flag: `parser.telemetry.enabled` (default off)

## Release-first acceptance criteria

- Current state: some services collect ad hoc internal metrics, but no shared
  telemetry event/exporter abstraction exists.
- Production work: add bounded privacy-safe event primitives, a no-op default,
  exporter interface with parse-failure isolation, basic label/cardinality
  constraints, and payload/secret exclusion.
- Sequence: after P08-US01; foundation for P08-US03/US04.
- Basic validation: telemetry disabled is inert, one event reaches a test
  exporter without document content, a failing/slow exporter does not fail the
  parse, oversized/forbidden fields reject or redact, and rollback disables it.
- Deferred: exhaustive privacy/adversarial analysis, load/backpressure
  campaigns, detailed exporter overhead/RSS, retained manifests, and
  environment proof.

Source payloads and credentials must not enter telemetry; that is required
production behavior, not deferred validation.

## User story

As a service operator, I want bounded telemetry primitives isolated from parser
execution, so that later instrumentation cannot leak content or make parsing
depend on an exporter.

## Business value

A safe telemetry foundation enables diagnosis and capacity planning without
adding document-egress, cardinality, or availability risk.

## Problem statement

The parser has processing metadata and logs but no shared metric contract,
label policy, bounded queue, or exporter-failure boundary for production
instrumentation.

## In scope

- Counter, gauge, histogram, timing, and structured-event primitives.
- Controlled metric names, dimensions, units, and bounded-cardinality labels.
- Content/secret redaction and prohibited-field checks.
- Non-blocking exporter queue, timeout, backpressure, and failure isolation.
- Parse-scoped correlation without document-derived metric labels.

## Out of scope

- Instrumenting all parser stages or quality decisions.
- Selecting a monitoring vendor or creating dashboards.
- Recording document text, filenames, prompts, crops, or raw evidence.

## Technical approach

Define an internal telemetry interface with an in-memory test exporter and
bounded asynchronous delivery boundary. Allowlist labels and make the disabled,
backpressured, and failed-exporter paths deterministic no-ops for parsing.

## Acceptance criteria

1. Telemetry primitives enforce documented name, unit, type, and label schemas.
2. Labels reject document text, filenames, hashes, prompts, crop bytes, secrets,
   and unbounded identifiers in all privacy-canary tests.
3. A failed, slow, or full exporter never fails parsing and observes approved
   queue, timeout, and drop behavior.
4. Disabling `parser.telemetry.enabled` performs no exporter calls and produces
   no JSON or Markdown difference.
5. Parse correlation uses an approved bounded mechanism and is absent from
   metric dimensions when it would create unbounded cardinality.
6. Primitive overhead is recorded before and after for diagnosis; exporter
   non-blocking behavior, queue bounds, and resource limits remain independent
   gates.

## Dedicated tests

- Unit tests: primitive types, schema enforcement, redaction, cardinality,
  queues, timeouts, drops, and exporter isolation.
- Integration tests:
  [tests/stories/phase_08/test_p08_us02_telemetry_primitives.py](../../../tests/stories/phase_08/test_p08_us02_telemetry_primitives.py).
- Negative tests: content canaries, secret canaries, invalid dimensions, slow
  exporter, raised exporter, and queue saturation.
- Contract tests: telemetry on/off leaves public JSON and Markdown unchanged.
- Fixture-based tests: synthetic parses containing document-text, filename,
  prompt, crop, secret, cardinality, and exporter-failure canaries.
- Configuration tests: disabled default, queue bounds, timeouts, and invalid
  exporter settings.
- Performance tests: enabled/disabled primitive overhead for diagnosis and the
  paired LlamaParse gate for end-to-end candidate latency.

The sole operative latency benchmark is
[`latency-reference-v1.md`](../../benchmarks/llamaparse-15/latency-reference-v1.md).
Primitive/exporter microbenchmarks are diagnostic only. Before Definition of
Done, every semantically comparable case requires at least five interleaved
candidate/Llama samples; candidate p50 and nearest-rank p95 must each be no
greater than the paired Llama values for that case, with no dropped failures or
corpus-average masking and unchanged required quality/reliability. A
non-comparable path is `Unmeasured/Blocked`; no local microbenchmark or
historical total substitutes. Privacy, exporter isolation, queue/timeout,
resource, default-off, and rollback gates remain independently blocking.

## API and schema compatibility

No public response change. Telemetry is an internal operational surface and
must not reinterpret processing metadata.

## Risks

- Queueing can retain data longer than intended.
- Cardinality mistakes can overload a monitoring backend.
- Hidden synchronous exporter work can add tail latency.

## Rollback

Disable `parser.telemetry.enabled`; telemetry becomes a no-op while existing
application error logging remains.
