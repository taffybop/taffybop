- Current state: flags are individually defined in `Settings`; there is no
  centralized owner/default/dependency/rollback registry.
- Production work: add a registry for shipping flags, validate enabled
  dependency combinations, expose safe defaults/ownership, and provide a
  deterministic operational disable path without changing current defaults.
- Sequence: Phase 08 foundation after the shipping Phase 04–07 flags are known;
  it may begin before P07-US09 is fully hardened if it enables nothing.
- Basic validation: registered defaults match current behavior, one valid
  dependency chain loads, one invalid combination fails clearly, one feature
  can be disabled/rolled back, and existing environment configuration remains
  compatible.
- Deferred: exhaustive flag-combination campaigns, full telemetry ownership
  evidence, independent review, and environment-specific rollout proof.

## User story

As a release operator, I want every optional parser behavior controlled through
one validated registry, so that I can enable and roll back capabilities without
rebuilding the service.

## Business value

Central controls reduce release risk across text repair, structured visuals,
models, and formats while preserving a known-good local-core path.

## Problem statement

Earlier phases introduce default-off behaviors with dependencies, artifact
requirements, and distinct fallbacks. Ad hoc settings do not establish complete
ownership, compatibility, or rollback contracts.

## In scope

- A typed registry for all Phase 01–07 behavior flags.
- Owner, default, scope, dependency, incompatibility, telemetry, review/expiry,
  and rollback metadata.
- Startup validation and a redacted effective-configuration record.
- Global and capability-specific kill switches.

## Out of scope

- Enabling an optional behavior by default.
- A remote flag-management service or administrative UI.
- Extraction or public-schema changes.

## Technical approach

Resolve existing settings through one registry, validate combinations before
serving traffic, and define deterministic precedence and kill-switch behavior.
Retain compatible environment names and expose only non-secret diagnostics.

## Acceptance criteria

1. One registry accounts for 100% of Phase 01–07 behavior flags.
2. Every entry declares owner, default, scope, dependencies, telemetry,
   rollback, and review/retirement metadata.
3. Unknown values, dependency violations, incompatible combinations, and cycles
   fail before parsing with actionable diagnostics.
4. All optional flags off reproduces approved P07 JSON and Markdown except
   excluded runtime metadata.
5. Every registered capability has a tested disable path that restores its
   documented fallback without schema or evidence corruption.
6. Effective configuration contains no secret or document-derived value.

## API and schema compatibility

No endpoint or response change. Supported environment variables remain
compatible; invalid configurations fail earlier and explicitly.

## Risks

- Incorrect precedence could enable an expensive or external route.
- A broad kill switch could disable unrelated local capabilities.
- Long-lived aliases can make configuration ambiguous.

## Rollback

Restore the previous settings-resolution path, keep optional features disabled,
and verify the P07 local-core fixture hashes.
