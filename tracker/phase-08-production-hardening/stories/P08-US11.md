## Release-first completion comment

Implemented strict, versioned, machine-checkable non-production release and
rollback manifests with allowlisted actions, assigned owners, ordered
prerequisites, expected results, abort conditions, exact evidence keys, and
next-owner approvals. The manifests bind the complete known-good and candidate
P08-US10 release-pin digests; their checked-in pin record is verified against
real local artifact-manifest, configuration, API-schema, and policy evidence,
so unavailable or invented identities fail closed. The P08-US10 decision now
validates its schema, full-pin bindings, flow coverage, blockers, selection,
and pass/block invariants before a candidate can enter the dry-run. Release
failure always retains known-good, and the rollback walk reports the exact
known-good selection after its documented artifact-selection step. The only
executor is an inert bounded walker: arbitrary command fields, shell actions,
network/deployment clients, extra evidence, stale pins, cycles, missing owners,
misrouted approvals, or out-of-order candidate selection are rejected.

Focused validation: `20 passed, 0 failed, 0 skipped, 0 deselected, 1 warning`;
cumulative Phase 08 validation through P08-US11: `186 passed, 0 failed, 0
skipped, 0 deselected, 1 warning`. The representative release happy path,
ordinary functional gate failure, and documented rollback/failure-state smoke
was `3 passed, 0 failed, 0 skipped, 0 deselected, 1 warning`. The warning in
each command was FastAPI's `StarletteDeprecationWarning` at
`.venv/lib/python3.13/site-packages/fastapi/testclient.py:1` for the deprecated
`httpx` TestClient integration. Public parse/API schemas were not changed by
the runbooks; the failed release retained the exact known-good pin and the
rollback walk restored it. No real deployment, live external call, production
mutation, or destructive command occurred. Production-scale rehearsals,
failure matrices, recovery-time qualification, campaigns, and independent
operational review were not run or claimed and remain deferred.

## User story

As an on-call operator, I want complete machine-checkable release and rollback
runbooks, so that promotion, containment, and recovery actions are ordered and
owned before a drill.

## Business value

Explicit runbooks reduce recovery ambiguity and make release approval dependent
on reproducible evidence rather than operator memory.

## Problem statement

Stories define individual fallbacks, but the complete preflight, canary,
promotion, stop, capability rollback, and full rollback sequence is not one
validated operational contract.

## In scope

- Preflight, canary, promote, observe, stop, capability rollback, and full
  rollback steps.
- Owners, prerequisites, commands/platform actions, approvals, abort criteria,
  communications, evidence, and recovery objective.
- Machine-checkable runbook manifest and known-good configuration references.
- In-flight request, cache, artifact, calibration, and schema considerations.

## Out of scope

- Executing the production-like drill.
- Selecting deployment orchestration software.
- Live production deployment or customer data.

## Technical approach

Represent required runbook fields and ordering in a validated manifest while
keeping human instructions concise. Bind every rollback target to the P08-US10
known-good identity and define observable completion checks.

## Acceptance criteria

1. Every runbook step declares owner, prerequisites, action, expected result,
   abort condition, evidence, and next approval.
2. Required ordering prevents promotion before P08-US10 passes and prevents
   recovery declaration before compatibility and fixture checks pass.
3. Capability rollback and full rollback identify immutable known-good
   artifacts, configuration, calibration, and policy versions.
4. In-flight requests, caches, schemas, external routes, telemetry failure, and
   review routing have explicit handling.
5. Recovery-time and evidence-completeness objectives are approved before
   P08-US12 becomes Ready.
6. Missing, cyclic, stale, or unowned steps fail runbook validation.

The recovery-time objective is an independently blocking operational safety
gate, not a parser-latency comparator. It cannot substitute for or waive the
sole operative
[`latency-reference-v1.md`](../../benchmarks/llamaparse-15/latency-reference-v1.md)
paired LlamaParse gate inherited from P08-US10; local stage/component timing
remains diagnostic only. Any applicable latency step must require at least five
interleaved candidate/Llama samples per case and retain
`Unmeasured/Blocked` when semantic comparability is absent.

- Configuration tests: capability and full known-good profiles.
- Fixture-based tests: test-only release/rollback manifest.

## Risks

- Machine-valid steps may still be operationally ambiguous.
- An incorrect known-good reference makes rollback unsafe.
