## Release-first acceptance criteria

- Current state: production has individual configured artifact identities but
  no unified versioned runtime/model/renderer/license release manifest.
- Production work: generate a deterministic manifest for shipped dependencies,
  native tools, OCR/model assets, renderers, schemas/prompts where applicable,
  versions/hashes/sources/licenses, and a basic build/startup verification.
- Sequence: after release dependencies are selected; may proceed in parallel
  with telemetry and must complete before hosted/release controls.
- Basic validation: manifest generation is deterministic, required shipping
  artifacts are listed, a missing/hash-mismatched required item blocks its
  feature or startup as designed, optional disabled items do not block, and
  rollback selects the known-good manifest.
- Deferred: fully reproducible-build proof, transitive supply-chain campaigns,
  exhaustive license/security review automation, immutable evidence custody,
  and environment attestation.

The selected release dependencies must still have a usable license/source;
only exhaustive proof is deferred.

## User story

As a release owner, I want every shipped runtime and model artifact inventoried
with integrity and license evidence, so that builds are reproducible and
unapproved components cannot ship.

## Business value

Artifact provenance reduces supply-chain, drift, redistribution, and rollback
risk across parser dependencies, Office tooling, OCR data, and models.

## Problem statement

Python dependencies are pinned, but model snapshots, OCR language data,
converters, native binaries, and license/notice evidence do not form one
complete release manifest.

## In scope

- Runtime, Python/native dependency, OCR-data, converter, and model inventory.
- Version, source, cryptographic hash, license status, and required notices.
- Required versus optional capability classification.
- Offline reproducibility and artifact-substitution checks.
- Machine-readable manifest plus human-reviewable summary.

## Out of scope

- Legal approval on behalf of counsel.
- Hosted privacy/egress policy.
- Canary quality comparison or release promotion.

## Technical approach

Generate the manifest from the candidate build and approved artifact sources,
verify it against packaged/runtime state, and fail closed for missing or changed
required components. Missing optional components must disable only their
capability with a documented fallback.

## Benchmark evidence — LlamaParse-15

- Cases/regions: expert outputs count derivative screenshots/crops as images on
  vector-only cases; our Uber output correctly counts 27 embedded images but
  also uses classifier/OCR/render artifacts whose exact versions determine
  descriptions, classifications, and OCR.
- Current behavior: document asset origin and output-producing runtime/model/
  renderer identity are not always traceable together, making drift and
  generated-as-source semantics hard to audit.
- Generalized behavior: shipped OCR data, classifiers, captioners, models,
  converters, and renderers are pinned in the release manifest and linkable
  from processing provenance; native document assets remain distinct from
  derivative runtime outputs.
- Acceptance/tests/metrics/performance: approved manifest positive,
  source-document assets as non-targets, and missing/hash/license/origin/
  optional-fallback negatives; independently bound artifact size and record
  startup/validation timing for diagnosis.
- Gaps: `GAP-VISUAL-001`, `GAP-PROVENANCE-001`,
  `GAP-COVERAGE-001`, and `GAP-PERFORMANCE-001`.

## Acceptance criteria

1. The manifest covers 100% of shipped runtime dependencies, native binaries,
   OCR data, converters, and model artifacts.
2. Every entry includes version, source, cryptographic hash, required/optional
   status, license review state, and notice obligation.
3. Missing, changed, unknown, or hash-mismatched required artifacts fail the
   gate with an exact component reason.
4. An unavailable optional artifact disables only its capability and records
   the documented fallback.
5. A local-only build can reproduce and validate its manifest without network
   access.
6. The manifest contains no document content, secret, or user-specific cache
   path.
7. Every output-producing OCR/classifier/captioner/model/converter/renderer
   version referenced by processing provenance resolves to one manifest entry;
   embedded source assets and per-document derivative crops/renders are not
   miscounted as shipped runtime artifacts.

## Risks

- Transitive native artifacts can be missed by package-only inventories.
- License metadata may require human interpretation.
- Upstream artifacts can drift under an unchanged name.

## Rollback

Block the candidate and retain the known-good pinned artifact set. Optional
capabilities with failed evidence remain disabled.
