# Immediate Affected-Benchmark Validation Gate

Status: **Mandatory after every production fix and before defect closure**  
Execution input: **The complete benchmark PDF or PDFs affected by the active defect**  
Manual review scope: **The declared defect impact boundary plus bounded collateral changes**  
Captured surfaces: **complete raw Markdown, actual rendered UI/DOM, and full public JSON**

## Purpose

Every defect correction must be proven against the benchmark document that
exposed it immediately after the production change. Focused tests establish
the capability contract, but they do not prove that the relevant public output
is corrected in a complete parse. A defect therefore cannot move from
`Validating` to `Done` until its affected full-PDF rerun passes this targeted
gate.

This is a local closure gate. It does not replace unrelated-PDF controls, wave
drift screens, genericity evidence, or the final frozen all-15 campaign. It is
not an exhaustive manual audit of every feature in the affected PDF; broad
document-wide review belongs to the wave and final all-15 gates.

## Trigger and scope

Run this gate after:

1. the focused regression fails on the pre-fix behavior;
2. the generic production correction is implemented;
3. the focused, variant, negative, adversarial, and relevant shared-family
   tests pass; and
4. the candidate code and frontend build used for capture are identified.

Use the affected cases named in the defect card and the active slice in
`execution-order.md`. Always submit each **complete PDF**, even when the
reviewed discrepancy is confined to one page or region. A partial-page or
page-range parse cannot close the defect. When a root-cause card has multiple
case slices, each slice must pass its own affected-PDF gate; the card may close
only after every affected slice has passed on one integrated build.

Before the run, the defect card must declare a bounded **validation target**:

- the affected case, page(s), region(s), component(s), DOM/JSON selectors, and
  source oracle;
- each recorded symptom and its expected source-grounded result;
- the raw Markdown, rendered UI/DOM, and JSON paths whose content, structure,
  ordering, ownership, or presentation can express that symptom; and
- bounded collateral paths/components that the changed capability can
  reasonably affect.

Do not expand this local gate into a manual feature-by-feature review of
unrelated tables, forms, charts, diagrams, images, or prose in the same PDF.

## Required fresh captures

Create a new immutable attempt directory. Never overwrite the pre-fix evidence
or a failed attempt. Record the source SHA-256, byte size and page count; run
ID and timestamps; service source/build identity and feature profile; frontend
build, browser and viewport; LlamaParse project, settings and job ID; and a
hash for every retained artifact.

For every affected PDF, submit the same source bytes to both systems and
preserve:

### LlamaParse reference

- Raw Markdown bytes exactly as returned or downloaded.
- Full original JSON response bytes without normalization or field removal.
- The actual rendered Markdown UI as displayed by LlamaParse: full-page and
  relevant-region screenshots plus DOM/rendered representation where the
  browser permits it.
- Referenced images/assets and request/job metadata needed to reproduce the
  displayed result.

### Service under test

- Raw Markdown response and canonical full Markdown as separate artifacts;
  they must be byte-identical unless a reviewed public contract explicitly
  says otherwise.
- Full original public JSON response bytes before any comparison projection;
  it must validate context-free against the public model/schema.
- The actual Clearleaf rendered output generated by the candidate frontend:
  serialized post-render DOM, full-page and relevant-region screenshots, and
  referenced assets. A generic Markdown renderer is not an acceptable
  substitute.
- Request/HTTP metadata, service profile and candidate build identity.

If a required reference or rendered surface cannot be captured, the attempt is
`blocked`; absence is not evidence that the issue is resolved.

## Required targeted comparison

Use the complete captured outputs, but manually compare the defect card's
declared validation target. Each relevant surface receives an explicit
pass/fail decision. A surface may be marked `not_applicable` only when the
capability contract proves the defect cannot be represented there; preserve
that surface's complete artifact and record the rationale.

### Raw Markdown

Within the declared pages, regions and structural paths, compare the Markdown
elements relevant to the defect: content and order, headings, paragraphs,
lists, tables or forms, visual placement, links, emphasis, Unicode, escaping,
significant whitespace, duplication, or omission as applicable. Confirm
service raw Markdown and canonical full Markdown parity. Unrelated Markdown
features need not receive manual adjudication at this gate unless the
whole-output drift scan reports that they changed.

### Rendered UI and snapshots

Compare the actual LlamaParse and Clearleaf presentations at the declared
pages, regions, elements and DOM paths for the visual or semantic properties
relevant to the defect, such as order, grouping, hierarchy, alignment,
meaningful spacing, merged cells, captions, visual placement, image-derived
text, or exactly-once presentation. Inspect both screenshots and DOM/rendered
structure when the symptom can appear in both; neither a text diff nor a
visually similar image can waive a failure on a relevant representation.

### Full JSON

Compare the original responses semantically at the declared JSON paths and
related components, even when their schemas differ. Review the properties
relevant to the defect, such as page association, type/order, nesting,
text/OCR, cells/spans, form controls, visual structures, relationships,
coordinates, evidence/provenance, or serialized content. Preserve normalized
comparison views separately; they must never replace the original response.

### Whole-output drift scan and bounded collateral review

Run automated structural diffs over the **complete** pre-fix and post-fix
service Markdown, rendered snapshot/DOM, and JSON, with the fresh LlamaParse
outputs available for adjudication. The scan is a detector, not a substitute
for the targeted manual review.

Manually inspect:

1. every change inside the declared validation target;
2. the bounded collateral paths named in the defect card; and
3. every unexpected change reported outside those boundaries.

Unchanged, unrelated areas do not require manual re-review at this local gate.
Any unexpected material change must be source-adjudicated, recorded, and
either shown to be harmless or treated as a regression/new defect. This keeps
the immediate check specific to the fix while still detecting collateral
damage.

### Source-grounded decision and collateral review

LlamaParse is the requested baseline, while the PDF is source truth. Do not
copy LlamaParse prose, values, table structure or visual relationships that
are unsupported by the PDF. Confirm that every material symptom attributed to
the active defect is gone on every relevant surface and that the automated
whole-output scan plus bounded collateral review finds no new material
regression caused by the fix.

## Attempt result

Each attempt records exactly one result:

- `pass` — every issue-specific acceptance criterion passes on each relevant
  Markdown, rendered UI/DOM, and JSON path; any `not_applicable` surface has a
  documented contract rationale; automated whole-output drift and bounded
  collateral review find no new material regression; all artifacts and hashes
  are present.
- `fail` — any attributed symptom persists, any required surface disagrees,
  public output is invalid, or the correction introduces a material regression.
- `blocked` — a required parse, artifact, UI capture, source oracle or review is
  unavailable.

On `fail`, keep the evidence, return the defect to `In Progress`, correct the
generic capability and create a new immutable attempt. On `blocked`, keep the
card out of `Done` until the missing evidence is available. A unit-test pass,
one corrected surface, a page-only parse, or an aggregate similarity score can
never produce `pass`.

## Required closure record

The defect card must link an immutable comparison record containing:

- defect ID, active slice and affected case IDs;
- the declared validation target and bounded collateral paths;
- source, candidate build, settings and job identities;
- hashes and paths for all reference and service artifacts;
- per-surface `pass`/`fail`/`not_applicable` findings and issue-specific
  assertions;
- the complete-output automated drift report, plus the disposition of every
  changed target/collateral path and every unexpected changed area;
- reviewer, review timestamp and final attempt result; and
- explicit confirmation that this local pass does not waive the remaining
  control, wave, genericity or final all-15 gates.

Only a passing record may satisfy the card's immediate affected-benchmark
closure checklist.
